# Superseded research: Maven-only feasibility for Android runtime conformance

**Status:** Historical analysis only. Issue #36 selects Gradle and explicitly prohibits Maven for the Android workflow. Do not use the Maven feasibility findings or proof-of-concept steps below as current implementation guidance. This file records no Android execution evidence; the completed Gradle runtime results are in [`docs/reports/issue-36/20260927T025037Z/`](../reports/issue-36/20260927T025037Z/).

## Finding

Maven can compile the shared Kotlin/JVM verifier and can orchestrate device commands. Android devices and emulators can run instrumentation APKs without Gradle: Android documents both on-device/emulator instrumented tests and the direct `adb shell am instrument` path. API 26 and API 37 runtime targets are available through Android's SDK/emulator channels.

The unresolved part is producing the required **test-only Android-library instrumentation APK** with a supportable Maven build. Android's documented Android build flow is the Android Gradle Plugin (AGP), which supplies the build tasks for APKs and Android libraries; Android's library-test workflow packages the library and its dependencies into a test APK and installs only that test APK. I found no first-party Android Maven build plugin or current official Maven recipe for that topology.

The upstream third-party [Simpligility Android Maven Plugin](https://simpligility.github.io/android-maven-plugin/plugin-info.html) does expose APK-building and device-instrumentation goals. But its latest documented release, 4.6.0, dates to 2019-05-08, and its SDK-platform documentation only enumerates numeric levels through 19. Its documentation does not establish API 26/API 37 toolchain support or the standalone Android-library test-APK behavior required here. It is a candidate for a disposable proof of concept, not a verified implementation choice.

**Historical conclusion (superseded):** At the time of this research, Maven-only appeared technically possible as a custom build integration but lacked a verified APK/instrumentation path. The current Issue #36 decision is Gradle-only; do not use Maven for its Android harness.

| Android API 26 | The sole API 26 target is `Medium_Phone`, using `system-images;android-26;google_apis_playstore;x86` (32-bit x86). Android's emulator acceleration guide permits x86 images on x86_64 hosts for API 10+, and local `emulator -accel-check` reports KVM usable. No other API 26 image or physical-device fallback is in this scope. [Emulator acceleration](https://developer.android.com/studio/run/emulator-acceleration), [SDK image metadata](https://dl.google.com/android/repository/sys-img/google_apis/sys-img2-1.xml). |
| Android API 37 | The selected target is the available `Pixel_9` AVD using the Android 37.2 Google APIs Play Store x86_64 image with 16 KB page size. Report API level, exact image revision, ABI, and build fingerprint; “API 37” alone does not identify the image. [Android 17 SDK setup](https://developer.android.com/about/versions/17/setup-sdk), [get Android 17](https://developer.android.com/about/versions/17/get). |
| Real instrumentation execution | Android says instrumented tests run on physical devices or emulators. Its command-line guide documents installing the test package and running `adb shell am instrument -w <test_package>/<runner>`. Thus the runtime test itself is not inherently tied to a Gradle invocation; a Maven lifecycle can invoke ADB after producing the APK. [Instrumented tests](https://developer.android.com/training/testing/instrumented-tests), [command-line tests](https://developer.android.com/studio/test/command-line). |
| Test-only Android library topology | Android documents that an Android library's test APK includes the library and its dependencies, with no separate app under test; the Android `androidTest` task installs only that test APK. The documented implementation is AGP-based. Simpligility documents an `android:instrument` goal, but I found no current evidence it supports this same standalone library-test topology. This is a key unresolved acceptance criterion, not just a task-name substitution. [Android library testing](https://developer.android.com/studio/projects/android-library). |
| Kotlin 2.4.20 / JDK 17 / Java 8 bytecode | The existing `interop/kotlin/pom.xml` already pins Kotlin Maven Plugin 2.4.20, compiles with Java release 8, and sets `kotlin.compiler.jdkRelease=1.8`; the repository's existing contract runs Maven on JDK 17+. Kotlin's first-party Maven compiler documentation says `jvmTarget=1.8` selects Java 8 bytecode, while `jdkRelease=1.8` also constrains available JDK APIs. This is a viable compile layer, but it does not package/Dex an Android APK; the resulting classes still need an Android packaging toolchain. [Kotlin Maven compiler options](https://kotlinlang.org/docs/maven-kotlin-compiler.html), [Kotlin Maven support](https://kotlinlang.org/docs/maven.html), [existing POM](../../interop/kotlin/pom.xml). |
| BC 1.86 / Jackson Core 2.22.2 | The existing POM and lockfile already pin these exact versions. The BC 1.86 source has an AnimalSniffer check against Android API 26 signatures for base/release-8 classes; that is static API-surface screening, not execution on ART. Jackson's project README states Android SDK 26+ for 2.14 and later; that is useful minimum-version evidence, not a runtime result for the exact 2.22.2 jar. The Android test APK must package the resolved runtime jars and actually exercise them on both targets. [BC API check](https://github.com/bcgit/bc-java/blob/r1rv86/gradle/animalsniffer.gradle), [Jackson Core README](https://github.com/FasterXML/jackson-core/blob/2.x/README.md), [existing POM](../../interop/kotlin/pom.xml). |
| Maven wrapper and dependency/plugin checksums | Existing Maven Wrapper 3.9.16 configuration pins both the distribution and wrapper JAR SHA-256 values. Apache documents `distributionSha256Sum` and `wrapperSha256Sum`. Existing `lockfile.json` records SHA-256 checksums for the Maven dependencies and 10 Maven plugins, including Kotlin Maven Plugin 2.4.20 and Maven Lockfile 5.18.3. The upstream lockfile project supports dependency checksums and plugin locking (enabled by default). These controls can cover AndroidX test dependencies and Maven packaging plugins when added and locked. They do **not** cover Android SDK/build-tools/emulator packages downloaded outside Maven; pin and record those separately. [Maven Wrapper checksums](https://maven.apache.org/wrapper/), [Maven Lockfile](https://github.com/chains-project/maven-lockfile), [existing wrapper properties](../../interop/kotlin/.mvn/wrapper/maven-wrapper.properties), [existing lockfile](../../interop/kotlin/lockfile.json). |

## Historical Maven-only proof-of-concept proposal (not selected)

The following steps record the rejected Maven-only experiment for historical context. Do not execute them for Issue #36; the selected Android workflow is Gradle-only.

1. Keep Maven Wrapper 3.9.16 and Kotlin Maven Plugin 2.4.20; compile the shared verifier source at Java 8 bytecode level. Package the canonical vector as a test APK asset from its existing repository path; do not copy or fork the vector/verifier.
2. Produce one standalone instrumentation test APK containing the verifier, AndroidJUnitRunner/JUnit 4 tests, the vector asset, and the locked BC/Jackson runtime dependencies. An option to investigate is a Maven POM that invokes pinned Android SDK tools through Maven executions/plugins (or the old Simpligility Android Maven Plugin). APK construction must include resource/manifest processing, DEXing, alignment/signing, and dependency inclusion; this is custom/unverified unless the candidate plugin passes the tests below.
3. Install and run it only on `Medium_Phone` (the sole API 26 x86 target) and `Pixel_9` (Android 37.2/API 37 x86_64) using ADB/`am instrument`. No physical device or other emulator image substitutes. Verify that only the test APK is installed for the library test, capture `ro.build.version.sdk`, image/build fingerprint, ABI, SDK/build-tools revisions, command, and test reports, and run the same positive and negative conformance cases on both.
4. Lock every Maven dependency and build plugin with SHA-256 and preserve wrapper checksums. Provision SDK packages/images by explicit package/revision and record their official source/checksum separately; Maven's lockfile does not lock them.
5. Stop if either image cannot build/install/run the same standalone test APK, if a main production app is required, or if exact dependencies fail on-device. This Maven-only path is superseded and must not be used.

Historical assessment only: passing the rejected proof of concept would have established a narrow, pinned Maven-only path for the named test APK and device images—not universal Android compatibility. This analysis is superseded; use the selected Gradle-only path for Issue #36.
