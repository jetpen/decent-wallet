# ADR-0003: Explicit wallet-container v1-to-v2 migration

**Status:** Accepted

**Scope:** One-way migration of the immediately preceding wallet-container format.

## Context

ADR-0002 introduced container v2 so the rotation-dispatch intent is authenticated as part of both DEK wrapping and payload encryption. A v1 reader could ignore an unknown payload field and continue signing; therefore, a migrated v2 file must remain unreadable to v1 implementations. ADR-0002 initially rejected v1 files without migration and explicitly left Issue #18's migration criterion incomplete. The Issue #18 contract requires an explicit, authenticated, one-way migration from the immediately preceding format, rejection of unknown versions and downgrades, and preservation of the previous valid file on failure. The repository owner authorized this migration as a separate contract.

The v1 input format is the wallet-container implementation immediately preceding v2 (including its encrypted active and pending signing-key fields). No production wallet files are stored in the repository. The migration test vector is a synthetic v1 container generated by that prior implementation.

## Decision

- Version 2 remains the current wallet-container format. Version 1 is accepted only as input to explicit migration; other unsupported older or newer versions are rejected.
- `Wallet.migrate_container(path, password, *, inactivity_minutes=5)` authenticates exactly one v1 container, migrates it in place to v2 with the same password, and returns the migrated wallet unlocked. Migration uses the v1 version-bound AAD to authenticate the DEK and payload, then rewraps the DEK and encrypts the unchanged wallet content using v2 AAD.
- Migration is never implicit. `Wallet.open()` and `Wallet.import_container()` remain v2-only; callers must explicitly migrate a v1 file before opening it or importing its v2 bytes. `migrate_container()` rejects current v2, older unsupported versions, and newer versions; it provides no downgrade path.
- The migration writes only after authentication, payload validation, and construction of the v2 candidate. It uses atomic same-directory replacement. Wrong passwords and invalid containers leave the original v1 bytes untouched. A failed write whose rollback is verified restores the original bytes and returns `StorageFailure`; if rollback or its directory sync cannot be verified, it raises the value-free `StorageOutcomeUnknown` rather than claiming that either version is safely persisted. No decrypted backup is written to disk.
- Successful migration replaces the source with v2. This is intentionally one-way for older implementations: v1 software cannot open the resulting v2 file because the version is authenticated. Separate v1 backups or copies remain outside the wallet's ability to revoke.

## Consequences

- The no-migration decision in ADR-0002 is superseded only for the explicit v1-to-v2 method above. The v2 dispatch-intent, authenticated-version, and fail-closed direct-open/import requirements remain.
- An application that receives a v1 export as bytes must first place it at the chosen wallet path and call the explicit migration operation; direct v1 import continues to fail closed.
- The migration criterion is implemented in the Python core only. Native platform adapters, cross-platform conformance, and production Registry transport/deployment verification remain separate Issue #18 acceptance work.
